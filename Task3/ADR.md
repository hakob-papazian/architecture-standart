### **Функциональные требования**

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
| UC1 | Потенциальный клиент, Сайт, Система кол-центра | Подача заявки на депозит через сайт | Клиент открывает сайт → видит список депозитов с актуальными ставками → заполняет форму (ФИО, номер телефона) → подаёт заявку. Сайт передаёт заявку в Систему кол-центра. Менеджер кол-центра звонит клиенту, предлагает условия. Новый клиент должен посетить отделение для идентификации. |
| UC2 | Существующий клиент, Интернет-банк, АБС | Подача заявки на открытие депозита в интернет-банке | Клиент входит в интернет-банк → видит список депозитов с актуальными и персонализированными ставками → выбирает депозит, указывает счёт и сумму → подаёт заявку. |
| UC3 | Клиент, Интернет-банк, СМС-шлюз | Подтверждение операции через СМС-код (OTP) | Интернет-банк запрашивает у СМС-шлюза одноразовый код → клиент получает СМС → вводит код в интерфейсе → заявка подтверждается. |
| UC4 | Менеджер бэк-офиса, АБС | Обработка заявки на депозит (MVP) | Менеджер бэк-офиса видит входящие заявки в АБС → изучает заявку → подтверждает ставку → АБС открывает депозит. |
| UC5 | АБС, СМС-шлюз, Клиент | Отправка СМС-уведомлений клиенту | После подтверждения менеджером ставки АБС отправляет СМС клиенту. После открытия депозита АБС отправляет финальное СМС. |
| UC6 | Сотрудники бэк-офиса депозитов и кредитов, АБС | Управление ставками депозитов в АБС | Сотрудники ведут актуальные ставки в АБС (замена XLS-файлов). Разграничение доступа по ролям. |

### **Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| NFR1 | Доступность всех сервисов 24/7, SLA ≥ 99,9% |
| NFR2 | При сбое основного ЦОД интернет-банк переключается на резервный ЦОД без потери доступности |
| NFR3 | Передача данных на сайте и в интернет-банке — только по HTTPS (TLS) |
| NFR4 | Время отклика пользовательских операций — миллисекунды; загрузка справочных данных — не более 300 мс |
| NFR5 | Интернет-банк не обращается напрямую к АБС — нагрузка на Oracle DB АБС не должна возрасти |
| NFR6 | АБС масштабируется только вертикально; горизонтальное масштабирование — только на стороне интернет-банка |
| NFR7 | Все изменения реализуются на существующем стеке банка (.NET, Java, MS SQL, Oracle) или совместимых технологиях |
| NFR8 | СМС-функционал (OTP и уведомления) реализуется командой банка без изменения ядра платформы подрядчика |
| NFR9 | Документация для всех новых и изменённых компонентов |

### **Решение**

#### Диаграммы C4

- **c4_context.drawio** — Диаграмма контекста (C4 Level 1): внешние участники, системы и их связи в рамках MVP.
- **c4_containers.drawio** — Диаграмма контейнеров (C4 Level 2): детализация интернет-банка и АБС, новые компоненты и интеграции.

---

#### Ключевые архитектурные решения

**1. Deposit Integration Service — буфер между интернет-банком и АБС**

Прямая интеграция интернет-банка с АБС недопустима (NFR5): БД Oracle АБС уже перегружена. Вводится новый лёгкий .NET-сервис — **Deposit Integration Service**, который:
- Периодически синхронизирует ставки депозитов из Oracle АБС → кэширует в MS SQL интернет-банка. Интернет-банк читает ставки из собственной БД, без вызовов АБС.
- Асинхронно переносит поданные заявки из MS SQL интернет-банка → в Oracle АБС для обработки бэк-офисом.

Технология: .NET (банк обладает экспертизой). Сервис разворачивается на стороне интернет-банка.

**2. СМС OTP в Deposit Module (без изменения ядра платформы подрядчика)**

Функционал OTP реализуется в новом **Deposit Module** — расширении интернет-банка, разрабатываемом командой банка (.NET). Модуль использует существующий СМС-шлюз через HTTP API. Ядро платформы подрядчика не затрагивается (NFR8).

**3. Ставки депозитов переводятся в АБС**

В АБС создаётся новый PL-SQL модуль управления ставками — **Rates Management Module**. Он заменяет XLS-файлы, обеспечивает совместный доступ (с разграничением прав) для сотрудников бэк-офиса депозитов и кредитов. Разрабатывается командой АБС.

**4. Подача заявок с сайта — через Систему кол-центра**

Сайт передаёт заявки напрямую в существующую Систему кол-центра (Java Spring Boot API). Менеджер кол-центра работает в привычном интерфейсе. Новая интеграция не требуется.

**5. Kafka и микросервисы — отложено до пост-MVP**

Текущая версия интернет-банка (ASP.NET MVC 4.5 / .NET 4.5) несовместима с Kafka. Введение Kafka и микросервисной архитектуры на этапе MVP создаёт избыточный риск. Для MVP используется паттерн «таблица-очередь» на MS SQL. Переход на Kafka и микросервисы планируется на следующем этапе (финальная архитектура, через год).

### **Альтернативы**

| Альтернатива | Причина отклонения |
|---|---|
| Прямая интеграция интернет-банка с API/БД АБС | БД Oracle АБС перегружена; прямые вызовы при росте онлайн-нагрузки создают риск недоступности всего банка (NFR5) |
| Kafka как брокер сообщений для MVP | Текущая версия платформы интернет-банка (.NET 4.5) несовместима с Kafka; внедрение потребует замены ядра (подрядчик) или рефакторинга монолита — неприемлемо для MVP |
| Хранение заявок с сайта напрямую в АБС | Система кол-центра уже умеет принимать заявки и назначать операторов; дополнительная интеграция сайта с АБС избыточна |
| Реализация модуля депозитов силами подрядчика (изменение ядра ИБ) | Создаёт зависимость от подрядчика, увеличивает стоимость и сроки; банк имеет собственную .NET-экспертизу для разработки расширения |

**Недостатки, ограничения, риски**

| # | Описание |
|---|---|
| 1 | **Задержка передачи заявки в АБС.** Deposit Integration Service синхронизирует данные по расписанию (polling). Между подачей заявки клиентом и её появлением в АБС возможна задержка (секунды–минуты). В рамках MVP (ручная обработка бэк-офисом) это приемлемо. |
| 2 | **Новый компонент — новый риск.** Deposit Integration Service — новый сервис без production-истории. Требуются нагрузочное тестирование и мониторинг. |
| 3 | **АБС масштабируется только вертикально.** Даже при наличии буфера, при значительном росте заявок Oracle DB АБС может стать узким местом. |
| 4 | **Монолит интернет-банка.** Обновление ядра платформы ИБ зависит от подрядчика. Deposit Module разрабатывается как расширение, но остаётся в рамках монолита — ограничивает независимое масштабирование. |
| 5 | **Персональные данные.** Сбор ФИО и телефона на сайте требует соответствия 152-ФЗ: политика конфиденциальности, согласие на обработку ПДн, безопасное хранение. |
