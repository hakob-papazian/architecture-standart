# FURPS+ — MVP онлайн-подачи заявки на депозит, Банк «Стандарт»

| Код | Требование | Комментарий |
|-----|------------|-------------|
| **F** | **Функциональные (Functionality)** | |
| F1 | Сайт: отображение списка доступных депозитов с актуальными ставками для потенциальных клиентов | |
| F2 | Сайт: подача заявки на депозит с указанием ФИО и номера телефона | |
| F3 | Сайт: заявка передаётся в систему кол-центра; менеджер кол-центра связывается с клиентом и может предложить особые условия | |
| F4 | Новые клиенты, пришедшие с сайта, обязаны пройти личную идентификацию в отделении банка | Требование регулятора: банк не вправе принять нового клиента без проверки документов |
| F5 | Интернет-банк: отображение списка депозитов с актуальными ставками и персонализированными ставками для конкретного клиента | |
| F6 | Интернет-банк: подача заявки на открытие депозита с указанием счёта и суммы | |
| F7 | Интернет-банк: подтверждение операции через СМС-код (OTP) | Функционал СМС реализован в ядре системы; доработку выполняет команда банка без привлечения подрядчика |
| F8 | Клиент получает СМС-уведомление после подтверждения менеджером ставки по депозиту | |
| F9 | Клиент получает СМС-уведомление после открытия депозита | |
| F10 | MVP: менеджер бэк-офиса депозитов обрабатывает заявку и подтверждает условия депозита в АБС | На этапе MVP ручная обработка сохраняется; автоматизация — следующий этап |
| F11 | АБС: ведение ставок по депозитам (замена XLS-файлов); доступ для сотрудников бэк-офиса депозитов и кредитов с учётом разграничения прав | Текущее решение на XLS не масштабируется, не поддерживает аудит и совместную работу |
| F12 | АБС: автоматизация процесса согласования ставки по заявке (сокращение ручного обмена письмами между отделами) | |
| **U** | **Удобство использования (Usability)** | |
| U1 | Пользовательский интерфейс сайта и интернет-банка должен быть максимально удобным для клиента | |
| U2 | Интерфейс должен соответствовать корпоративной дизайн-системе (фирменные цвета, брендированные элементы) | Единая дизайн-система снижает когнитивную нагрузку и поддерживает узнаваемость бренда |
| U3 | Все пользовательские операции должны выполняться с минимальным откликом (целевое значение — миллисекунды) | |
| U4 | Устранить текущую проблему: справочные данные при проведении платежей загружаются дольше 1 секунды | Влияет на воспринимаемую скорость системы; целевой показатель — не более 300 мс |
| **R** | **Надёжность (Reliability)** | |
| R1 | Все сервисы должны работать 24/7 с уровнем доступности не менее 99,9% (SLA) | |
| R2 | При сбое основного ЦОД сервисы интернет-банка должны оставаться доступными за счёт переключения на резервный ЦОД | Интернет-банк в настоящее время работает на одной группе серверов в одном ЦОД — необходимо изменить |
| R3 | Предусмотреть горизонтальное масштабирование и балансировку нагрузки между серверами, приложениями и ЦОД | АБС исключение: масштабируется только вертикально из-за ограничений Oracle |
| R4 | Новый процесс подачи заявки не должен обращаться напрямую к API/БД АБС — ввести промежуточный слой (очередь или сервис) | БД АБС уже перегружена; прямые вызовы при росте онлайн-нагрузки могут нарушить работоспособность банка |
| **P** | **Производительность (Performance)** | |
| P1 | Время отклика всех пользовательских операций — миллисекунды | |
| P2 | Загрузка справочных данных при проведении операций — менее 300 мс (устранение текущей проблемы с задержкой > 1 с) | Рекомендуется кэширование справочных данных на уровне интернет-банка |
| P3 | Онлайн-нагрузка от заявок на депозиты не должна создавать дополнительного давления на БД АБС | АБС масштабируется только вертикально; необходим буфер (очередь/кэш) перед АБС |
| **S** | **Поддерживаемость (Supportability)** | |
| S1 | Разработать техническую документацию для всех изменённых и новых компонентов системы | Необходимо для дальнейшего расширения и передачи знаний внутри команды |
| S2 | При доработках максимально использовать технологический стек, уже применяемый в банке (MS SQL, Oracle, .NET, Java) | Снижает риски интеграции, стоимость обучения и сопровождения |
| S3 | Новые технологии и библиотеки должны быть совместимы с существующими платформами разработки | |
| S4 | Внутренние сотрудники должны обладать достаточной экспертизой в применяемых технологиях | Снижает зависимость от подрядчиков и ускоряет разработку |
| **+R** | **+ Ограничения (Restrictions)** | |
| +R1 | Передача данных на сайте должна осуществляться по HTTPS (TLS) — сайт собирает чувствительные персональные данные (ФИО, телефон) | Требование 152-ФЗ «О персональных данных»; сбор ПДн без шифрования недопустим |
| +R2 | Передача данных в интернет-банке должна осуществляться по HTTPS (TLS) — передаются финансовые данные и реквизиты счетов | |
| +R3 | Функционал СМС (OTP и уведомления) реализуется командой банка без изменения ядра платформы подрядчика | Изменение ядра интернет-банка требует привлечения подрядчика и создаёт зависимость |
| +R4 | Ядро платформы интернет-банка (ASP.NET MVC 4.5 / .NET 4.5) обновляется только подрядчиком — новый функционал реализуется без изменений ядра | Архитектурное ограничение монолита на платформе подрядчика |
| +R5 | Рассмотреть переход модуля открытия депозитов интернет-банка на микросервисную архитектуру | Позволяет независимо масштабировать новый функционал и использовать Kafka; монолит несовместим с Kafka |
| +R6 | В качестве брокера сообщений использовать Kafka (на перспективу); совместимость с текущей версией интернет-банка отсутствует | Необходимо учесть при проектировании микросервисного слоя |
| +R7 | АБС масштабируется только вертикально из-за ограничений Oracle DB — горизонтальное масштабирование АБС невозможно | Ключевое архитектурное ограничение: новые процессы не должны увеличивать нагрузку на АБС сверх допустимого |
